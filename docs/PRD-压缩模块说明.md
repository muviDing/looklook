# 视频压缩模块 — 交互设计与技术设计

---

## 一、核心交互设计

### 1.1 压缩模式选择
- 单选框，默认选中"感知无损"，另有"完全无损"可选。
- 每种模式配说明，悬停问号可弹出详细说明。

### 1.2 批量压缩进度展示
- 显示进度条、成功/失败/待压缩数量。
- 点击数量可切换左侧抽屉，显示对应文件卡片列表。
    - 成功卡片：显示"原大小→新大小""已节省xxMB"
    - 失败卡片：红色标签说明错误原因
    - 待压缩卡片：蓝色底，仅文件名

### 1.3 勾选项
- **自动打标签**（默认勾选）：原文件标记"压缩前"，新文件标记"已压缩_感知无损"或"已压缩_完全无损"。
- **压缩成功自动删除原文件**（可选）：原文件移入回收站，应用中移除。
- **启用GPU加速**（可选，默认不勾选）：勾选后尝试GPU加速，若硬件不支持则压缩直接失败，文件和记录恢复原状。

### 1.4 任务控制
- 支持"暂停/继续""关闭"操作。
- 暂停时，当前正在压缩的视频任务终止，相关缓存（临时文件）自动清理，未完成的任务回退为待压缩。
- **继续后，重新读取当前弹窗中的压缩参数**，从下一个未完成任务重新开始，允许用户在暂停期间修改压缩模式、GPU设置等选项。

### 1.5 文件与记录管理流程
- 定义：
    - A：原视频文件
    - B：应用中原视频记录（与A同名）
    - C：正在生成的新视频文件
    - D：新视频文件的应用记录

#### 压缩流程与回滚机制
1. 用户仅有A（文件）和B（记录）。
2. 勾选B发起压缩，生成C（临时文件，命名为A+后缀）。
3. 压缩期间：
    - 若压缩失败/用户取消/暂停：C被自动清理删除，A和B无变化（状态回滚）。
    - 若压缩成功：
        - A和B重命名为"{A原文件名}_原文件"
        - C重命名为"{A原文件名}"
        - 自动生成D（应用记录），D继承B的应用属性（标题、标签、演员、评分、观看次数、最后观看时间、备注、上映时间）
4. 若用户勾选了自动删除原文件，则将A移入回收站，B移除管理
5. 若用户勾选了自动打标签，则给D自动打上对应标签（若B未移除，也打上对应标签）。

## 二、核心技术设计

### 2.1 压缩任务管理
- 单任务串行，每完成一个视频才进入下一个。
- 每个任务原子性执行，未完成的不产生残留文件。
- 进度、状态、统计始终与实际文件/记录一致。

### 2.2 文件操作与命名
- 压缩期间生成的C命名为"A_正在压缩"或"A_tmp"等，防止与A冲突。
- 压缩成功后：
    - A物理文件重命名为"A_原文件"
    - B的文件名同步更改为"A_原文件"
    - C重命名为"A"
    - 导入生成D，文件名与C一致，属性从B深拷贝
- 失败/暂停/取消时：
    - C自动删除
    - A、B均不变

### 2.3 应用属性同步
- D继承B所有应用属性字段（标题、标签、演员、观看次数、最后观看时间、备注、上映时间等）。
- 标签打标自动完成，根据压缩模式自动标注。

### 2.4 GPU加速
- 若用户勾选"启用GPU加速"，则ffmpeg命令参数自动切换为GPU编码参数（如 hevc_nvenc, h264_nvenc 等）。
- 启动前先检测硬件能力（如调用ffmpeg -hwaccels/ffmpeg -encoders 检查）。
- 若检测到不支持，立即判定压缩失败，流程回退、无冗余文件。
- 若支持，正常压缩，提升速度。

### 2.5 其他技术细节
- 进度条通过监听ffmpeg输出实时更新。
- 临时文件、缓存文件统一存储到指定临时目录，失败/中断时主动清理。
- 删除原文件时采用"移入回收站"策略，调用系统API，保证可恢复。
- 任务异常/中断/强制关闭时，自动回滚所有未成功任务。

## 三、伪流程图

1. 勾选B → 点击压缩 → 生成C（A+后缀名，临时）
2. 压缩期间
    - 失败/取消/暂停：C删除，A/B未变，任务进度回退
    - 成功：A/B重命名加"_原文件"，C重命名为原名，导入D（属性继承），A/B和C/D均为新旧一一对应
3. 自动打标签、可选删除原文件、可选GPU加速，均在流程内完成判断和处理

## 五、特殊情况处理

- GPU不支持时，压缩直接失败，所有文件与记录回滚。
- 批量任务每完成一个视频才计为"成功"，UI进度与真实处理同步。
- 暂停/中断/取消均确保无冗余文件，状态一致。
- 应用崩溃/强退后，重启自动扫描清理残留C文件。

## 六、压缩模式技术实现方案

### 6.1 高效感知无损模式

#### 6.1.1 标准模式（CPU）
- **编码器**: `libx265`（H.265/HEVC）
- **视频参数**:
  - CRF: 28（平衡质量与文件大小的合理值，H.265比H.264的CRF值通常高4-6）
  - 预设: `medium`（平衡压缩速度与质量）
  - 配置: `-c:v libx265 -crf 28 -preset medium`
- **音频参数**:
  - 编码器: AAC
  - 比特率: 128kbps
  - 配置: `-c:a aac -b:a 128k`
- **其他优化**:
  - 快速启动: `-movflags +faststart`（优化网络播放）
  - 输出格式: MP4
  - 像素格式: `-pix_fmt yuv420p`（保证兼容性）

#### 6.1.2 GPU加速模式（NVIDIA）
- **编码器**: `hevc_nvenc`（NVIDIA硬件加速H.265）
- **视频参数**:
  - 预设: `p4`（质量优先预设）
  - 配置文件: `main`
  - 码率控制: `vbr`（可变比特率）
  - 质量控制: `-rc:v vbr -qmin 0 -qmax 28 -b:v 0`
  - 配置: `-c:v hevc_nvenc -preset p4 -profile:v main -rc:v vbr -qmin 0 -qmax 28 -b:v 0`
- **音频参数**: 与标准模式相同
- **其他优化**: 与标准模式相同

### 6.2 完全无损模式

#### 6.2.1 智能无损策略
- **优先级1：流复制（Remux）**
  - 检测原文件编码格式，如果视频流已经是H.264/H.265且音频流是AAC/FLAC等高效格式
  - 使用`-c copy`直接复制流，仅重新封装容器
  - 配置：`-c:v copy -c:a copy -avoid_negative_ts make_zero`
  - 适用场景：原文件已经是高效编码，只需优化容器格式

- **优先级2：视频流复制+音频重编码**
  - 视频流使用`-c:v copy`，音频重编码为高效格式
  - 配置：`-c:v copy -c:a aac -b:a 128k`
  - 适用场景：视频编码已经高效，但音频格式需要优化

- **优先级3：完全重编码**
  - 当流复制无法减小文件大小时，使用无损重编码
  - 标准模式（CPU）：`-c:v libx264 -crf 0 -preset medium -c:a flac`
  - GPU模式（NVIDIA）：`-c:v h264_nvenc -preset p1 -rc constqp -qp 0 -c:a flac`

#### 6.2.2 完全无损模式实现流程
1. **格式检测**：使用ffprobe分析原文件的视频/音频编码格式
2. **策略选择**：根据检测结果选择最优的无损策略
3. **试验性压缩**：先执行选定策略，检查输出文件大小
4. **策略降级**：如果文件大小未减小，自动降级到下一个策略
5. **最终验证**：确保输出文件小于原文件，否则标记为失败

### 6.3 压缩前检查流程
- **输入文件检查**: 验证文件存在且可读
- **输出路径检查**: 确保输出目录存在，若无则创建
- **空间检查**: 检查目标磁盘剩余空间是否足够
  - 高效感知无损模式：至少需要原文件大小的50%
  - 完全无损模式：至少需要原文件大小的100%
- **GPU支持检查**: 对于GPU模式，先检测系统是否支持相应编码器
  - 执行: `ffmpeg -encoders | findstr nvenc` 检测是否有NVIDIA编码器支持
  - 若无支持，立即标记为失败，错误原因为"硬件不支持GPU加速"

### 6.4 压缩后验证流程
- **文件大小检查**：压缩完成后，比较输出文件与原文件大小
  - 如果输出文件大小 >= 原文件大小，标记为失败
  - 失败原因：`"压缩后文件大小未减小（原文件：{原大小}，压缩后：{新大小}），可能原文件已经高度优化"`
- **文件完整性检查**：验证输出文件可以正常播放
- **自动删除原文件**：仅在压缩成功且文件大小确实减小后执行

### 6.5 错误处理与提示
- **常见错误类型与提示**:
  - GPU不支持: "您的硬件不支持GPU加速，请使用标准模式"
  - 格式不支持: "视频格式不被支持，请尝试其他格式"
  - 空间不足: "目标磁盘空间不足，无法完成压缩"
  - 权限不足: "无法访问或修改文件，请检查权限设置"
  - 源文件损坏: "源视频文件已损坏，无法进行压缩"
  - 编码错误: "视频编码过程出错: {具体错误信息}"
  - **文件大小未减小**: "压缩后文件大小未减小（原文件：{原大小}，压缩后：{新大小}），可能原文件已经高度优化"

### 6.6 标签管理规则
- **原文件标签**: "压缩前"
- **新文件标签**:
  - 高效感知无损: "已压缩_高效感知无损"
  - 高效感知无损+GPU: "已压缩_高效感知无损_GPU"
  - 完全无损: "已压缩_完全无损"
  - 完全无损+GPU: "已压缩_完全无损_GPU"

### 6.7 进度解析实现
- 通过解析ffmpeg标准错误输出获取进度信息
- 解析如下格式的输出: `frame= 1000 fps= 25 q=28.0 size=10240kB time=00:00:40.00 bitrate=2097.2kbits/s speed=1.0x`
- 计算公式: `进度百分比 = (当前处理时间 / 视频总时长) * 100`
- 每200ms更新一次进度显示

## 七、性能优化建议

### 7.1 文件类型适配
- 对于已经高度压缩的文件（如H.265编码的文件），在完全无损模式下考虑直接复制视频流而非重新编码
- 对于非常规分辨率视频，自动调整参数以确保兼容性
- 对于超大分辨率视频（如4K以上），提供可选的降采样选项

### 7.2 长视频处理优化
- 提供当前文件实时压缩进度显示
- 对于超过30分钟的视频，显示预计完成时间
- 长视频处理时保持系统唤醒状态，防止系统休眠中断处理

## 八、暂停继续机制优化

### 8.1 参数动态更新
- 用户暂停压缩后，可以在弹窗中修改压缩模式、GPU设置、自动标签、自动删除等选项
- 点击"继续"时，系统重新读取当前弹窗中的所有参数设置
- 后续未完成的任务将使用新的参数设置进行压缩
- 已完成的任务不受影响，保持原有的处理结果

### 8.2 状态同步机制
- 暂停时保存当前进度状态，包括已处理、成功、失败的任务列表
- 继续时传递新的参数配置，但保持进度状态不变
- 确保UI显示与实际处理状态完全一致

## 九、自动删除原文件机制

### 9.1 删除条件
- 压缩成功完成
- 新文件大小小于原文件大小
- 用户勾选了"压缩成功时自动删除原文件"选项

### 9.2 删除流程
1. **文件移动**：使用`shell.trashItem()`将原文件移入系统回收站
2. **记录删除**：从数据库中删除原视频记录（B记录）
3. **UI更新**：通知前端更新视频列表，移除已删除的记录
4. **错误处理**：如果删除失败，记录错误日志但不影响压缩任务的成功状态

### 9.3 安全保障
- 使用系统回收站而非直接删除，确保文件可恢复
- 删除操作在压缩完全成功后才执行
- 删除失败不会影响压缩任务的成功状态
- 详细记录删除操作的日志，便于问题排查
